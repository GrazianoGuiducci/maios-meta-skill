# Meta-Activity — practical operating knowledge

## Give the activity an entry it can actually use

When assigning work to a new or existing activity, let the competence responsible for that work shape the assignment. Reach its operating body, practical guide, current sources and retained reasons. A short entry connects purpose, present work, needed knowledge, available means, useful return and recovery. Include essential knowledge in the prompt if the next receiver cannot access files. A competence name or inaccessible link cannot supply its method.

Use useful understanding in the present work. Let a new source or consequence change the question, sources or method while the work forms, and return reusable learning to the responsible competence. A later wake can refine that understanding; it is not a condition for using it now. Keep project knowledge with the project and general operating knowledge with the competence.

## Distinguish the requested profile from the saved configuration

Identify the actual controller and job, its owner and receiving context. Read the trigger or cadence, timezone, enabled state and notification settings it exposes. When the host supports model or reasoning settings, read those too. Record a preference separately when the controller cannot set or attest it. A requested model or local instruction is not evidence of the model selected by the scheduler. Preserve fields outside the selected change and any concurrent work.

## Preserve the configuration when it changes

The project's guide explains why the activity works; a recovery copy preserves the instructions and settings actually saved in the controller. Keep both recoverable in their appropriate locations. Use a private, access-controlled archive already owned by the receiving environment. The public kit contains the method, not anyone's private job configuration.

For a newly created job, read the full installed prompt and all recovery-relevant fields the controller actually exposes after it confirms creation. Save that readback as a distinct version. For an existing job, reread it before a selected native change and preserve the complete previous configuration if no matching recovery copy exists. A draft or a summary of changed clauses is not that copy.

After the authorized change, read the actual job again and save a new immutable version with the full resulting prompt, stable job ID, capture time, native update time when exposed, raw trigger or schedule, timezone, state, receiver association and supported settings. Retain disabled or expired jobs as disabled or expired when they belong to the selected backup scope. Preserve native field names and values; mark unavailable fields instead of inventing them. Include every field the host needs to reconstruct the observable job, without claiming access to hidden delivery settings or past runs.

Do not serialize credentials into the archive. If a prompt itself contains a secret, protect it before export and retain an explicitly redacted copy with its recovery limitation. A private repository is not permission to copy secrets. The archive's access and location must be appropriate for the private instructions it contains.

Read back the saved archive and compare its prompt and settings with the captured controller state. In a versioned repository, retain the commit and file identity so the captured version can be found again. Maintain a small recovery index reaching the latest qualified copy and the retained predecessor. Reread the controller when concurrent editing can have changed the job. If it has moved, record the difference and reconcile the observed version; do not label an older archive current or overwrite another editor's work.

## Handle missing access and external edits precisely

When an authorized change has occurred but the private archive cannot be written, retain a precise backup-pending note: job identity, changed fields, observed controller revision or time, intended private destination and the access needed to finish. When the controller cannot be read, a project file does not establish its current configuration. Continue independent work and keep the actual missing operation explicit.

A change made directly in another interface is not automatically archived. At the next relevant authorized movement, compare the real controller with the saved copy. The method does not install a watcher or a backup job. An unchanged wake, a domain finding or an update to the project's guide does not require another full configuration snapshot.

## Restore the selected activity from its present

A saved copy does not enable, recreate or move a job. Before a selected recovery, identify any surviving job and compare the saved configuration with current intent, current project knowledge and completed effects. Choose the exact restore, replacement, enablement or rescheduling action that is already entrusted, and obtain a missing operator decision only for the remaining effect. Preserve a deliberate pause. Read back the restored configuration and archive that new result; do not treat restoring instructions as proof the job has run.

## Changing the receiving context

Recovering a working guide in another chat and moving a scheduled job are different operations. Recover the job's actual controller identity, original purpose, editable instructions, retained knowledge, trigger, timezone, receiving association and any in-flight work. Inspect which of those associations the controller can actually change. Keep the present job if a separate working conversation already supplies the needed context.

If a replacement is selected, retain the outgoing state, completed effects and pending work. Coordinate a cutover so both jobs cannot perform the same effect. Preserve a recovery route if the new receiver cannot resume. A saved configuration proves configuration; observe the first real wake and its contribution before treating the transfer as exercised. A chat that cannot wake itself must hand back a reusable operating note rather than claim persistent monitoring.

## Compose a service through its work

A client-search activity can connect source research, qualification, a durable record, authorized contact, reply monitoring and useful notifications. Let the context determine which functions belong together. An outreach record needs enough identity and effect history to avoid duplicate contact; a research activity may instead preserve a question, source coverage and useful differences. An empty cycle can end quietly when it adds no useful contribution. Keep unresolved work and the condition that would make it actionable.

When an outcome changes the method, update the responsible competence and the instructions actually consumed by the next wake. Changing the scheduler's label does not change an unreachable method. Keep a useful capability when a particular campaign ends; retire or reshape the recurring activity when its contribution is exhausted and that change is entrusted. Written method, archived configuration, observed execution and later assimilation retain their different meanings.
